## Claim

If this were done, portfolio-manager-service would reject a unit's room type change when the unit has ongoing reservations or reservations checking in or out today (confirmed or reserved), and would run the same check for every unit added to or removed from a room type on the room type detail page. Kontrol UI would show the two popups ("Move unit to another room type" and "Move units to another room type", with links to the multicalendar and the reservations list). The premise still holds: units can still be moved between room types today.

## Evidence

- `portfolio-manager-service` @ `2fc96897`, `service/src/lm-units/lm-units.status-validator.ts:85`: the only reservation check for units is in the status validator. It runs `getOngoingOrFutureReservationsForUnit` when the status becomes DEACTIVATED or TEMP_OFF and throws "Unit deactivation failed: unit has active reservations". That is the existing rule the ticket wants to copy.
- `service/src/lm-units/lm-units.service.ts:239`: a `roomTypeId` change only calls `lmCombinedRoomTypesService.deleteSetsOnUnitChange`. No reservation lookup on a room type change.
- `service/src/lm-room-types/lm-room-types.status-validator.ts:69`: room type deactivation has the same kind of check, nothing for changing the unit list.
- Searched all HSP repos on `origin/<default>` for the popup copy ("can't be moved to another room type", "Move unit to another room type", "Move units to another room type"): no hits. The only "has active reservations" text in `kontrol-ui` is for combined room types (`room-type-combined-details-main-section.tsx:292`), a different feature.
- Not checked: the legacy `kontrol` Vue app's unit pages, and whether kontrol-api's reservation move flow protects the guest some other way. A "unit moved between RTs" event does not exist in the repos searched.
