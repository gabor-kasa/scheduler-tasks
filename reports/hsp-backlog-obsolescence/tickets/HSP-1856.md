## Claim

Done means: on a unit in PMS, a user can record a bed that is not in a bedroom (as the room type's "Common spaces" does), so a studio can be described correctly. What would make it moot: the unit already has an equivalent field.

## Evidence

- The unit has an equivalent field, under a different name. `portfolio-manager-service` @ 259df2a2 `service/src/json-schemas/unit/living-room.json-schema.ts:28` defines `livingRoom.sleepOptions` ("Living room sleep options": bed type plus quantity). The room type's `commonSpace` is at `roomType/sleeping-arrangements.json-schema.ts:57` with the same bed type and count shape.
- It predates the ticket. `kontrol-ui` commit 93cc3f49 (2023-03-17, "KC-3505 - livingRoom.sleepOptions") added it, 20 months before the report.
- The PMS UI renders it. `kontrol-ui` @ e2a78ae2 `libs/kontrol-ui/pages/portfolio/src/lib/components/unit-details/sections.tsx:833` has the "Living room" section with `sleepOptions`.
- Later work made it count. HSP-3449 (2026-04-29, #2544) auto-computes bed counts including living room sleepers (`sections.tsx:449`), warns when unit beds differ from the room type (line 453), and shows "Additional sleeper(s)/bed(s) are added to the living room!" (line 475). The unit's bedroom count is derived from the `bedrooms` array (line 500), so a unit with no bedrooms shows 0, not 1.
- Searched: portfolio-manager-service, kontrol-ui portfolio pages. Did not check the ALL property's actual unit data, and did not open the live PMS.
