## Claim

If this were done, kontrol-api would have an endpoint taking a property id and a date range and returning reservations that overlap the range, are currently in GXO, and were moved there from that property. It depends on the fields from HSP-666 or an equivalent history lookup.

## Evidence

- `kontrol-api` @ `845c5c84`, `service/app/components/reservation-v2/reservation.routes.ts:87-96`: the GET routes are list, unassigned-summary, search, check-in-issue-report, search-groups, export, index-settings, `/:id`, extension-availability and unit-before-overflow/availability. No route filters by "moved to GXO from property". A search for `movedFrom`, `originProperty` and `fromProperty` in `kontrol-api` and `portfolio-manager-service` found only the overflow move notes (`reservation-note/overflow-move-note.ts:29`).
- Same Duetto evidence as HSP-666 (shared investigation, see that file): `dynamic-revenue-service` @ `fa0e563` cancels in Duetto when a reservation moves to GXO (`egress-event-handler.service.ts:282`, `301d782`, 2024-10-10, #285) and rebuilds the original property from history (`api-data-provider.ts:1614`). That is a push on each move, where this ticket asked for a pull query by property and date range.
- Not checked: whether any consumer (Duetto reconciliation, Looker, finance) still needs the pull query, and `kontrol-serverless` or BigQuery as alternative places for such a lookup.
