## Claim

The problem: an overbooked, unassigned reservation in a room type blocks a check-in/check-out change on a reservation that is already assigned to a unit, although the unit itself is free on the multicalendar. The proposed fix (per Adam): when modifying dates of an assigned reservation, look only at the unit's availability, not room type availability. If solved, extending the check-out of an assigned reservation succeeds whenever its own unit is free, whatever the room type inventory says.

## Evidence

- `kontrol-api` @ `845c5c84`, `service/app/components/reservation-v2/services/reservation.update.service.ts:384`: when dates change on an assigned reservation (and `allowOverbooking` is false), the backend calls `checkUnitAvailableForReservation` for that reservation's own unit. It does not call a room type inventory check for this path (the other `checkInventory` uses are the inquiry-status path at line 128 and group children, `assertGroupChildChangeFits`, line 355).
- `service/app/components/reservation-v2/services/reservation.service.helpers.ts:569` and `service/app/components/unit-v2/services/unit.service.ts:120`: availability is computed from reservations that sit on a unit (`r.unit!`), so unassigned (overbooked) reservations are not counted. This is the unit-only check the ticket asked for.
- `kontrol-ui` @ `b1875b481`, `libs/kontrol-ui/pages/reservation-creator/src/lib/hooks/use-is-room-type-unavailable.ts:40`: the reservation editor still marks the room type unavailable from the room type availability API. The only exemption is `utils/availability-exemptions.ts:14` (`isInsideReservationDateRange`): same room type, same unit, dates inside the original range. Extending the check-out is not exempt, so the editor can still block exactly the case in the ticket. Added by HSP-4194 (`c7309907a`, 2026-09-29, #3127) for the submit re-check.
- `use-can-overbook.ts` shows the editor offers an overbooking path when inventory is exhausted (`availableWithOverbooking`), so GX has a workaround in the UI.
- Not checked: whether the legacy `kontrol` Vue multicalendar (`RoomTypeMoveDialog.vue`) behaves differently, and the version of this logic that existed in 2023 (kontrol-api history starts at the nx import commit `413be6f00`, 2026-05-13).
