## Claim

If this were done, the reservation creator in kontrol-ui would show an extra "reservation reference" input when the selected room type is a GXO (overflow) room type, and the value would be saved on the reservation. The description is the untouched story template, so what the reference points at (the original reservation, an OTA code, a Duetto id) is not written down anywhere on the ticket. The parent epic and the sibling tickets HSP-666 and HSP-667 suggest it is a Duetto helper: tie a manually created GXO reservation back to the booking it stands for.

## Evidence

- `kontrol-ui` @ `ac141aac`, `libs/kontrol-ui/pages/reservation-creator/src/lib/components/drawer/widgets/components/room-type-select.tsx:132,169`: the creator knows about GXO room types (`isOverflow`) but renders no reference input for them. A case-insensitive search of `libs/kontrol-ui/pages/reservation-creator` (non-spec files) for `reference`, `externalId`, `sourceReservation`, `channelReservation`, `reservationRef` and `referenceId` found nothing that is an input. The only `confirmationCode` hits are display of the reservation's own code.
- `db-schemas-ts` @ `9abcc67` (not in `default-branches.tsv`, read for context only), `src/schemas/reservation.schema.ts`: the only "reference" in the reservation schema is the `externalRefs.expedia_itinerary_reference` index (line 834). No field for a GXO-to-original-reservation link.
- Same Duetto evidence as HSP-666 (shared investigation, see that file): `dynamic-revenue-service` @ `fa0e563` (also outside the tsv, context only) cancels in Duetto when a reservation moves into GXO (`service/src/rms/events/egress-event-handler.service.ts:282`, `301d782`, 2024-10-10, #285) and rebuilds the pre-GXO room type and property from history. That path needs no reference typed in by a user.
