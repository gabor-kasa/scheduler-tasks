## Claim

If this ticket were done, a noise or smoke alert would reach the guest only once they are in the stay window defined by their `plannedArrival`,
with the static 3pm start moved to 4pm. Alternative that would make it moot: alerts gated on actual check-in status.

## Evidence

- `sensor-service` @ `947fc2cf`, `utils/alerts/query-helpers.ts:37-49`: `getActiveReservationByUnitAndDate` keeps a reservation only if the event time is
  at or after check-in date plus `plannedArrival` (and before check-out plus `plannedDeparture`). Fallback when `plannedArrival` is empty is
  `['15', '00']` (line 40), so the static 3pm is still there, as a fallback.
- All four handlers call it before sending anything: `functions/alerts/noise/noiseAlarmDetected.ts:28`, `noiseBreach.ts:47`, `noiseBreachEnded.ts:28`,
  `functions/alerts/smoke/smokeAlert.ts:34`. No active reservation in the window means the handler returns without a message.
- The gate is a time window, not the reservation status. `status` accepts `confirmed`, `checked_in`, `checked_out` (`query-helpers.ts:17`), so a
  confirmed guest who has not checked in yet is eligible after `plannedArrival`.
- The code came over with the 2026-04-15 merge of automessages into sensor-service (`beb45dd`, #143). The `plannedArrival` split goes back to 2021
  (`990b472`, iot-399). It predates this ticket (2023-11-20), so the "dynamic condition" half was probably already true when the ticket was written.
- Not checked: the Braze migration (HSP-240) moved guest-facing sends. I did not read the Braze side for its own timing rules.
