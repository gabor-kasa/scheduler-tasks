## Claim

If this were done, changing check-in or check-out dates on a reservation would check availability only for the added nights, so overbooking on a night
that is not changing would not block the save. Alternative that would make it moot: overbooked date changes are handled another way.

## Evidence

- `kontrol-api` @ `845c5c84`, `service/app/components/reservation-v2/services/reservation.update.service.ts:380-395`: when dates change on an assigned reservation (and
  `allowOverbooking` is false), `checkUnitAvailableForReservation` runs with the full new `checkInDateLocal` / `checkOutDateLocal`.
- `service/app/components/reservation-v2/services/reservation.service.helpers.ts:569-606`: that function passes the whole range to `getAvailableUnits`, ignoring
  only the reservation itself (`ignoredReservations: [existingReservationId]`, line 602). There is no added-nights or delta logic. A search for
  `addedNights|removedNights|changedDates|dateDelta` in `reservation-v2` found only the extension controller, which is a different flow.
- Gabor's 2025-11-11 comment cites `reservation.service.ts:450-465`. That code has since moved to the files above. I re-read the new location, so the conclusion is checked, not copied.
- What did change: HSP-2630 (`9dc427419`, 2026-02-16, #2726) makes a date change with `checkAvailability: false` unassign the altered or the conflicting reservations
  (`handleDateChangeConflicts`) instead of failing. Default saves still fail on a conflict, so this is a workaround, not the requested behavior.
- The ticket body itself says "TBD: discuss with stakeholders how they want these calculations to work". No decision was recorded.
