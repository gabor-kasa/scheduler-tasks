## Claim

If this were done, the reservation schema would have new fields for the original unit, room type and property, set when a reservation moves to GXO, left alone on moves inside GXO, nulled on a move back, backfilled by a script for reservations currently in GXO, and exposed on the reservation endpoints. The "why" is Duetto: send correct financial and inventory data per property, without a third place that unwraps the history by hand.

## Evidence

- `db-schemas-ts` @ `9abcc67`, `src/schemas/reservation.schema.ts`: no field for original unit, room type or property on a reservation (searched `gxo`, `overflow`, `original`). The fields were not built.
- `dynamic-revenue-service` @ `fa0e563`, `service/src/rms/events/egress-event-handler.service.ts:282`: when a reservation's new room type is GXO, the service sets `forceCancelDueToGXO`, so Duetto receives a cancellation. Added by `301d782` (2024-10-10, "Allow force cancel", #285).
- `service/src/rms/data/api-data-provider.ts:1614` (`reservationRoomTypeAndPropertyBeforeModifications`): rebuilds the pre-GXO room type and property by walking `history`, which is the manual unwrapping the ticket wanted to avoid. It is the Duetto consumer's own answer to the same need.
- `kontrol-api` @ `845c5c84`, `service/app/components/reservation-v2/services/reservation.overflow.service.ts:7` (`getOriginalUnitForReservation`) also derives the original unit from history, behind `GET /:id/unit-before-overflow/availability` (`reservation.routes.ts:96`).
- Not checked: whether Looker or the financial calculations (the other two "places" the ticket names) still unwrap GXO history by hand, and whether Duetto inventory per property is correct for reservations already in GXO.
