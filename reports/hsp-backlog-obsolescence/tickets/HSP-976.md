## Claim

The spike asks how to introduce "stay" (an ordered chain of consecutive reservations, same main guest, one id generated on the first reservation) as an entity, and how to handle splits, re-parenting, a cancelled root and pre-extensions. Done would mean a written design, and if built, a persisted stay id on reservations plus an API that returns the root reservation.

## Evidence

- A stay is computed, not stored. `kontrol-api` @ `845c5c84` `service/app/components/stay/stay.service.ts:12-35` (`getStays`) loads reservations, calls `getReservationExtensionGroup` per reservation and de-duplicates the groups. No stay id is generated or saved. Exposed as `GET /api/v2/stays` (`client/src/services/ReservationService.ts:709`).
- Consumers pass reservation ids as the stay id. `add-on-service` @ `7521ccee` `service/src/add-on-carts/add-on-carts.model.ts:26`: `stayId: Types.ObjectId; // Root reservation ID`, set at `add-on-carts.service.ts:174`. The guest-api add-on routes and guest-portal carry the same value (`guest-api` `service/src/components/add-ons/add-ons.routes.ts:76`).
- So the open questions in the ticket (split chain, cancelled root, pre-extension) are answered implicitly by whatever `getReservationExtensionGroup` does, not by a designed stay id. I did not read that function (it lives behind `reservation.repository.js`).
- No design doc is linked from the ticket. Not checked: Notion or Confluence for a stay spec.
- Date: `add-on-service` `stayId` since `ab0f282` (2024-04-10, HSP-786 repositories); kontrol-api history before the 2026-05-13 monorepo import (#2880) is squashed.
