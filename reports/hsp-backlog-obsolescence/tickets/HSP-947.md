## Claim

If this were done, booking email validation would let `unknown` results (reason `smtp_timeout`) through instead of failing the guest. On master that would be `unknown` in the allowed list, or a separate soft path for it.

## Evidence

- `guest-api` @ `e9e7a71a` `service/src/libs/mailgun-api-client/validate-email-address/validate-email-address.ts:22-27`: `allowedResults = ['deliverable', 'catch_all']`, and in production `isValid` is `allowedResults.includes(validationResponse.result)`. The ticket says the failing responses are `smtp_timeout / unknown`; whichever result string Mailgun sends for them, it is not `deliverable` or `catch_all`, so those addresses are `isValid: false` (I did not capture a live Mailgun response).
- `service/src/utils/joi/joi-mailgun-email.ts:33-49` turns `isValid: false` into an "Does not seem to be a valid email address" error, so the guest is blocked.
- Both booking paths call it: `service/src/components/booking/kbc/step-handlers/contact-details/contact-details.step-handler.ts:463,525,621,683` and `service/src/components/checkout/checkout.helpers.ts:280`. Only guest-api uses Mailgun validation (searched all HSP repos).
- Premise still holds: nothing retries or downgrades `unknown`; the only softening is the non-production `: true`. The email is not editable in some flows, which skips validation, but that is unrelated.
- History: `mailgunEmailValidation` has been there since `91c2c2af` (2021-01-26, EXT-860). Not touched for this since.
- Not checked: how many guests hit it today (needs prod logs for `got_email_address_validation_result` with `unknown`).
